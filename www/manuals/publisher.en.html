Publisher Integration Manual

For publishers who manage websites and apps on W8M, configure ad slots, and integrate using web ad code or the POST /pz interface.

1. Account and Traffic Resource Hierarchy

Publisher accounts manage websites, apps, and ad slots. The login page is at /goto/pub/e/....

Publisher Account
└── Traffic Source (website or app)
    └── Ad Slot

The dashboard shows top ad slots, top campaigns, and last-24-hour data. Reports are generated by backend logs and accounting jobs on a schedule, not real-time request-level data.

Registration and Password Recovery: You may need to complete Cloudflare verification to prevent bulk registration and spam. If verification expires, refresh the page. If you see "Too many requests," wait and try again—do not repeatedly click. For persistent issues, contact support@w8m.com.

The "Seller Transparency" section of your profile explains who sells your ad inventory, including seller ID, type, ad system identifier (ASI), public name, and domain. Information requires platform operator review; once approved, any changes revert to pending-review. These details are used in OpenRTB supply chains and report classification, but do not change revenue ownership, settlement entity, or payment method.

2. Create Traffic Source

Go to Traffic Sources and create new, then configure:

  • Name and Type: Web or App.
  • Bundle/Domain: for websites, use domain; for Android, use package name; for iOS, use store ID.
  • Environment and Standard ID: for websites, use review domain; for apps, use package name or app ID.
  • Public Review URL: provide only http or https pages without credentials.
  • Integration Method: choose ADX, web ad code, SDK, or server API, matching Web/App type.
  • Introduction URL, traffic scope (whitelist/blacklist), and enable status.
Web Source Verification: The Origin or Referer hostname in production pages must exactly match the site hostname in platform cache. Different subdomains are not automatically treated as the same site.

After modifying a traffic source, if the generated integration code is still rejected or uses old data, contact the operator to refresh the static cache; the ad request path does not query the database directly.

3. Create Ad Slot

Under your traffic source, select "Add Ad Slot" and configure name, width, height, floor price (USD CPM), language, device platform, page position, accepted media types, creative specs, quality conditions, category rules, and status.

  • Ad slot dimensions are runtime-trusted.
  • Browser or SDK self-reported dimensions cannot override platform config.
  • When request token dimensions differ from cache config, the service returns 400.
  • Floor price is the authoritative server-side minimum; requests can increase but not decrease; the higher value applies.
  • Select media type preferences, display position, rendering scenario, ad density, traffic audit status, resource source, and responsibility owner.
  • Refresh mode: none, periodic (15–3600 seconds), or event-triggered.
  • After changing dimensions, get new integration code; do not reuse old slot tokens.

4. Get and Deploy Web Ad Code

The ad slot list shows integration methods by traffic source type: Web shows only web ad code; App shows only SDK/API code. We recommend using the page-generated sample directly—site and slot are platform-generated identifiers; do not guess, truncate, swap, or manually edit them.

<script src="https://w8m.com/js/ads.js"></script>
<div id="pz-slot-13" style="width:300px;height:250px"></div>
<script>
pzLoadAds({
  "platform": "browser",
  "site": "<page-generated site token>",
  "adUnits": [{
    "code": "pz-slot-13",
    "slot": "<page-generated slot token>",
    "mediaTypes": {"banner": {"size": [300, 250]}}
  }]
});
</script>

ads.js defaults to inferring /pz from its script URL. If static files and ad service are on different hosts, specify explicitly:

pzLoadAds(payload, { endpoint: "https://w8m.com/pz" });

Deployment Notes

  • adUnits[].code is the page DOM element ID and response order flag, not resource identity; non-empty values must be unique per request.
  • site identifies publisher account and traffic source; slot identifies ad slot and dimensions.
  • Supported media types: banner, video, native.
  • Browser requests must send valid source; all source hostnames must exactly match cached site host.
  • /pz cross-origin requests have no credentials; rely on cross-origin cookies at your own risk.
Creative Isolation: ads.js places filled creatives in an independent sandbox iframe without allow-same-origin and marks containers as filled, no-fill, or error. Do not remove the sandbox or write response strings directly to the host page's innerHTML.

HTML Response

When responseFormat is omitted or html, success returns an array of HTML strings in ad slot order. Unfilled slots are empty strings:

["<iframe ...></iframe><img ...>", ""]
Valid requests return 200 even if fully unfilled. Hide or recycle empty-result containers; treat no-fill as normal, not a network error to retry quickly.

5. SDK and Server API Integration

SDK requests go to:

POST https://w8m.com/pz
Content-Type: application/json

Use actual tokens from the ad slot page's "API Code":

{
  "platform": "sdk",
  "responseFormat": "json",
  "site": "<page-generated site token>",
  "app": {"bundle": "example.com"},
  "adUnits": [{
    "code": "pz-slot-13",
    "slot": "<page-generated slot token>",
    "mediaTypes": {"banner": {"size": [300, 250]}}
  }]
}
  • This sample is context-only, deliberately omitting user and device identifiers. SDK can provide OpenRTB-style app, device, user, and regs objects.
  • device.ifa, device ID, user.id, and buyeruid enter local matching only when platform privacy policy permits personalization; context or restricted mode removes these.
  • Publishers must pass applicable GDPR/TCF, GPP/US Privacy, COPPA, and GPC/DNT/LMT signals from audited CMP/privacy flow; do not fabricate consent.
  • If providing app.id, app.bundle, or app.domain, they must match platform-verified traffic source identity.
  • SDK can omit Origin and Referer, but when present, they must pass host verification.
responseFormatResponse
Omitted or htmlOne HTML string per ad slot.
jsonOne structured fill/no-fill object per ad slot.
openrtbAn OpenRTB BidResponse; seatbid empty when fully unfilled.

Client is responsible for safely rendering adm per creative type and triggering measurement per protocol when using structured responses. Do not modify platform-generated signature parameters.

6. Browser Identity, Privacy, and Proxies

  • Browser integration uses aofei_pz_uid as a best-effort pseudonym identity only when the request passes configured personalization authorization.
  • Missing, refused, opted-out, invalid, COPPA, or unmapped GPP signals do not read or set cookies.
  • Missing cookies due to cross-origin policy do not block context delivery; the system does not concatenate IP and User-Agent as fallback identity.
  • SDK requests never read, set, or transmit that cookie; provide compliant device or user identifiers instead.
  • The service adopts X-Forwarded-For or X-Real-IP only when CDN or reverse-proxy egress has been whitelisted by the operator.
Publishers must not forge proxy request headers. If traffic flows through CDN or reverse proxy, jointly verify the proxy chain and true client address with the operator.

7. Fill, Measurement, and Reporting

Local creatives delivered via /pz reuse platform signature-based impression and click measurement. Accounting impressions and settlement amounts are based on valid impression tracking arrival; clicks on valid click tracking arrival. Bid prices use USD CPM (cost per thousand impressions); the accounting amount per valid impression is CPM / 1000; for example, a CPM of 2.5 counts as USD 0.0025.

When the platform enables external DSP/ADX demand-side bidding, local no-fill can use Fallback routing; external bidding competes with local creatives only when both the platform master switch and independent Always switch are enabled. These choices are transparent to publisher integration—no need to modify ads.js or request structure.

Market analysis shows data by traffic environment, integration method, media type, display position, refresh mode, quality classification, and authorized seller. Historical or unconfigured classifications explicitly show Unknown; unauthorized sellers do not appear under a seller ID. Reports are generated by log aggregation and accounting jobs on a schedule; when persistently missing, provide the operator with time range, traffic source, ad slot, and request result.

Settlement Invoice

The platform operator can generate publisher settlement invoices from completed daily accounting summaries, by UTC day, week, or month. Invoices go through draft, hold, confirm, settlement entry, or correction workflows; corrections to confirmed records preserve the original invoice and do not modify display facts.

For invoices or CSV exports, provide account ID and period to the operator. Do not send full card numbers, bank account numbers, or routing numbers through the dashboard, email, or support forms.

9. Launch Acceptance Checklist

  • Traffic source type, bundle/domain, site host, and status are correct.
  • Environment, standard ID, integration method, and public review URL are correct.
  • Ad slot dimensions, server-side floor, media types, display position, refresh, and quality rules are correct.
  • Seller information reviewed by platform operator; changes re-verified.
  • Web uses web ad code only; app uses SDK/API sample only.
  • Using latest-generated site and slot tokens from ad slot page.
  • Production page actual Origin/Referer exactly matches cached site.
  • Each non-empty code is unique in the request and has a corresponding DOM container.
  • Tested at least once with fill and once with no-fill response.
  • SDK does not rely on cookies; provides compliant device or user identifiers.
  • Confirmed with operator: cache refresh, report latency, and support contact.
